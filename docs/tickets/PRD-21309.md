## Product design

### Goals / Non-goals

- Goal: ship a first version of `intercom-mcp` that lets an agent read and act on the Intercom objects a support/CS workflow most needs — contacts, conversations, companies, tickets — through MSPbots' MCP gateway, with per-tenant credentials supplied by the gateway and never persisted by the connector.
- Goal: every write the agent makes (reply to a conversation, create/update a contact, create a ticket, reply to a ticket) is visible as a normal Intercom API call under the tenant's own Intercom account, so it shows up in Intercom's own audit trail — "every action logged" in the ticket's one-liner is satisfied by the platform's existing tool-call audit log (outside this repo) plus Intercom's own activity log, not by new logging this connector has to build.
- Non-goal (v1): deleting any Intercom object (contact, company, ticket) — not asked for, and higher risk than the rest of the surface; deferred, see Decisions.
- Non-goal (v1): Intercom's full query DSL for companies/segments, admin/team management, Articles (help-center content), custom-object workflows, webhooks/event subscriptions. These are real Intercom capabilities but outside what a "connect Intercom" listing implies as a first cut; can be added as follow-up tools without breaking v1's tool names or parameters.
- Non-goal: OAuth app installation flow. Intercom supports both OAuth apps and simple Personal Access Tokens; this connector uses the Header-credential model required by every MSPbots vendor-mcp repo (SOP §3.1) — see Tech design §5 for the exact header.

### Acceptance criteria

- AC1: Given valid Intercom credentials in the request headers, when an agent calls `initialize` then `tools/list`, then the response lists more than zero tools, every tool name starts with `intercom_`, and each tool's description is a single sentence starting with a verb.
- AC2: Given a request with the access-token header missing, when any `intercom_*` tool is called, then the response is HTTP 401 with a structured error body (`code: "not_configured"`) listing the required header name(s) — not a 500 and not a silent empty result.
- AC3: Given valid credentials, when the agent calls a read tool (contacts, conversations, companies, or tickets) with a filter that matches live data in the tenant's Intercom workspace, then the tool returns the matching records (paginated, `limit` honoured, `has_more` set correctly) reflecting Intercom's current state — not cached or stale data.
- AC4: Given valid credentials, when the agent calls a write tool (create/update contact, reply to a conversation, create a ticket, reply to a ticket), then the corresponding object is created/changed in the tenant's real Intercom workspace and the tool returns the resulting object's id and the fields that changed.
- AC5: Given the upstream Intercom API returns an error (401, 404, 422/400, 429, or 5xx), when a tool call hits that error, then the tool returns the structured error envelope with the matching `code` (`unauthorized` / `not_found` / `invalid_argument` / `rate_limited` / `upstream_error`) and never raises an unhandled exception; a 429 response is retried with backoff honouring `Retry-After` before being surfaced.
- AC6: Given no `X-Intercom-Region` header is sent, when any tool is called, then the connector talks to Intercom's default (US) API host and the call succeeds for a US-region workspace — region selection is opt-in, not required for the common case.
- AC7 (multi-tenant isolation): Given two concurrent tool calls carrying different tenants' Intercom credentials, when both are in flight at the same time, then each call only ever sees and only ever affects the Intercom workspace tied to its own request's credentials — no credential or response data leaks between the two requests.

## Tech design

### Conclusion

Build `intercom-mcp` from scratch (main line A, SOP `vendor-mcp-development` v11) against Intercom's public REST API (`https://developers.intercom.com/docs/references/rest-api/`), Python 3.12 + `uv` + FastMCP per the standard MSPbots vendor-mcp skeleton. Credentials travel only in request headers (access token + optional region); the connector is fully stateless and request-isolated per SOP §3. No new platform-side (MSPbots) code is touched — this is a pure new-repo build, `mcp-service-gateway` is read-only reference.

### Where the current implementation lives

Nothing exists yet beyond the README (`README.md` on `main`@`abc5237`, confirmed above). No prior MSPbotsAIFramework repo for Intercom. No platform code references Intercom.

Reference shape (same vendor-mcp pattern, for consistency, not copied): other `<vendor>-mcp` repos in `MSPbotsAIFramework` follow the SOP skeleton — FastMCP app exposing `POST /mcp` + `GET /health`, a `middleware.py` using a `ContextVar` to carry the per-request credential, a thin `client.py` wrapping the vendor's HTTP API, and `tools/<domain>.py` modules registering one `FastMCP.tool` per capability.

### Option analysis

| Option | How | Pros | Cost | Verdict |
|---|---|---|---|---|
| Header-credentialed REST wrapper (standard SOP shape) | Agent sends `X-Intercom-Access-Token` (+ optional region); connector calls `api.intercom.io` per request | Matches every other MSPbots vendor-mcp connector; no OAuth app registration with Intercom needed; tenants bring their own Personal Access Token the same day they sign up | Tenants must create an Intercom Personal Access Token themselves (Intercom Developer Hub) rather than click-through OAuth | **Chosen** — required by SOP §3.1 regardless; also the lowest-friction v1 for a listing with no stated OAuth requirement |
| OAuth 2.0 app flow (Intercom supports installable OAuth apps) | Register an Intercom OAuth app, gateway brokers authorize/callback, connector receives a short-lived OAuth token via header | Nicer sign-up UX (click "Authorize" instead of pasting a token) | Needs an Intercom Developer Hub OAuth app owned by MSPbots, app review by Intercom for some scopes, and gateway-side OAuth plumbing (`mcp-service-gateway`, out of this repo's reach — would need Leo) | Rejected for v1: no ticket requirement forces it, and it would turn a one-repo build into a cross-team gateway change |
| Fork/mirror an existing open-source `intercom-mcp` (several exist on GitHub) | Copy code, adapt headers | Faster bootstrap | SOP explicitly forbids forking/mirroring third-party MCP code (clean-room only, SOP rule 3); license/attribution risk | Rejected — policy violation |

### Data & API contract

Base URL by region (`X-Intercom-Region`, default `us`): `https://api.intercom.io` (us) / `https://api.eu.intercom.io` (eu) / `https://api.au.intercom.io` (au). Every call sets `Authorization: Bearer <X-Intercom-Access-Token>` and `Intercom-Version: 2.11`.

Representative tool → Intercom endpoint mapping:

| Tool | Intercom endpoint | Notes |
|---|---|---|
| `intercom_search_contacts` | `POST /contacts/search` | query by email/name; cursor pagination (`starting_after`) |
| `intercom_get_contact` | `GET /contacts/{id}` | |
| `intercom_create_contact` | `POST /contacts` | requires `email` or `external_id` (Intercom's own constraint, surfaced as `invalid_argument` if neither given) |
| `intercom_update_contact` | `PUT /contacts/{id}` | partial update, only sends provided fields |
| `intercom_search_conversations` | `POST /conversations/search` | filter by state (open/closed/snoozed), contact, date range |
| `intercom_get_conversation` | `GET /conversations/{id}` | includes `conversation_parts` (the full thread) |
| `intercom_reply_conversation` | `POST /conversations/{id}/reply` | `message_type`: `comment` (public reply) or `note` (internal); `admin_id` required by Intercom for admin-authored replies |
| `intercom_search_companies` | `GET /companies?name=` / `company_id=` | Intercom's company search is narrower than contacts/conversations; v1 exposes name/company_id filters only (see Decisions) |
| `intercom_get_company` | `GET /companies/{id}` | |
| `intercom_list_tickets` | `POST /tickets/search` | filter by state, contact, ticket type |
| `intercom_get_ticket` | `GET /tickets/{id}` | |
| `intercom_create_ticket` | `POST /tickets` | requires `ticket_type_id` (Intercom-side ticket type) and a contact |
| `intercom_reply_ticket` | `POST /tickets/{id}/reply` | same `comment`/`note` split as conversations |
| `intercom_list_admins` | `GET /admins` | used to resolve `admin_id` values the agent passes into reply/assignment calls |

Error envelope (all tools): `{"error": {"code": "...", "message": "...", "retryable": true|false}}`. Status mapping: `401 → unauthorized`, `404 → not_found`, `400/422 → invalid_argument`, `429 → rate_limited` (`retryable: true`, honours `Retry-After`), `5xx → upstream_error` (`retryable: true`). Missing credential header (connector-side, before any Intercom call) → HTTP 401, `code: "not_configured"`, body lists the required header name(s).

No database, no migration — this connector is stateless and has no storage of its own (SOP §1.3/§3.4).

Backward compatibility: not applicable — first version, no prior tool names or parameters to preserve.

### Key flow / sequence

```
Agent -> Gateway -> intercom-mcp /mcp (POST, headers: X-Intercom-Access-Token[, X-Intercom-Region])
  middleware: header present? no -> 401 {not_configured}; yes -> ContextVar{token, region}
  tool handler: build request via client.py (base URL from region, auth + version headers)
  client.py -> Intercom REST API
  Intercom response: 2xx -> shape into tool's compact JSON; 4xx/5xx -> errors.py envelope
  ContextVar reset in `finally` regardless of outcome
```

### Non-functional

- Idempotency/concurrency: all state lives in Intercom, not in this connector; concurrent calls are independent `httpx` requests sharing only a connection pool, never per-tenant state (SOP §3.3/§3.4) — tested explicitly (`tests/test_middleware.py` isolation test, AC7).
- Performance: `limit` default 25 / hard cap 100 on every list/search tool; responses serialized compact (`ensure_ascii=False`, no `indent=2`); oversized responses truncate with `has_more` rather than growing unbounded.
- Security: credentials never touch disk, env vars, or logs (only the `ContextVar`, request-scoped); `gitleaks detect` before every push; no vendor secrets ever committed (placeholders only in README examples).
- Multi-tenant isolation: isolation is per-request via the gateway (the gateway, not this connector, maps a tenant to a credential) — this connector's only obligation is to never let one request's `ContextVar` leak into another's handling, which is the isolation test above.
- Observability: structured log line per tool call (tool name, HTTP status from Intercom, latency, **no** credential value) — the platform-level tool-call audit log (gateway) is the system of record for "every action logged" from the ticket's one-liner; this connector's own logs are for debugging upstream failures, not the audit trail itself.

### Effort & breakdown

Story points: 3
Tier: cross-service flow, security/tenant isolation, many acceptance scenarios (row "3") — new MCP microservice talking to an external vendor API, with the SOP's mandatory per-request credential isolation as a core (not incidental) requirement, and 7 acceptance criteria across 4 resource domains.

Main uncertainty: exact Intercom rate limits and whether `POST /companies/search` (vs. the narrower `GET /companies?name=`) is available on the access-token scopes a typical tenant's Personal Access Token will have — resolved empirically once a real token is available; v1 uses the documented, scope-safe `GET /companies` filter rather than assuming the broader search endpoint, see Decisions.
Order inside this ticket: 1) skeleton + middleware + client + error mapping, 2) contacts tools (simplest resource, proves the pattern), 3) conversations tools, 4) companies tools, 5) tickets tools, 6) admins (read-only, smallest), 7) README + connector-wiki prep, 8) self-test + gates.

### Decisions made by DEV01

- No delete tools in v1 (contacts/companies/tickets are never deleted via this connector) — why: not asked for by the ticket, and destructive Intercom operations (especially company/contact deletion, which can cascade) carry more risk than the rest of the surface combined; alternative considered: full CRUD including delete, rejected as unnecessary scope expansion for a listing with no stated requirement.
- Company search uses `GET /companies` with `name`/`company_id` filters, not Intercom's broader search endpoint — why: the narrower endpoint is available on standard Personal Access Token scopes without extra app permissions; alternative: `POST /companies/scroll` (bulk export), rejected as built for data export, not point lookups an agent would make.
- `Intercom-Version` is a pinned server-side constant (`2.11`), not an agent-supplied header — why: this is a protocol-version pin, not per-tenant credential data; exposing it as a header the agent must know about would add implementation detail to the tool surface for no benefit; alternative: let it default to Intercom's oldest supported version (their behaviour when the header is absent), rejected because that silently drifts over time as Intercom deprecates old defaults.
- `X-Intercom-Region` defaults to `us` when absent rather than requiring it on every call — why: most Intercom workspaces are US-region; forcing every tenant to discover and send a region header for the common case adds friction with no benefit; alternative: hard-require the header, rejected.
- Reply tools take a `message_type` parameter (`comment` | `note`) instead of two separate tools per resource — why: keeps the tool count down (14 instead of 16) while mirroring Intercom's own API shape exactly, so the parameter is self-explanatory from Intercom's own docs; alternative: split into `intercom_reply_conversation` / `intercom_note_conversation`, rejected as unnecessary tool-count growth.
- Admins are read-only (`intercom_list_admins`) with no admin/team management tools — why: the only reason an agent needs admin data is to resolve an `admin_id` for a reply/assignment call; managing admins/teams themselves is an operator action, not something a support-workflow agent should do; alternative: full admin CRUD, rejected as out of scope and higher-privilege than the rest of the tool set.

### Risks & dependencies

- Risk: Intercom's rate limits (undocumented exact numbers at design time, generally per-app and burst-sensitive) could make bulk read operations (e.g. `intercom_search_conversations` over a large inbox) slow under retry/backoff. Mitigation: `limit` caps, 429 backoff honouring `Retry-After`, documented as expected behaviour rather than a bug.
- Risk: some Intercom endpoints require specific OAuth/API scopes that a given tenant's Personal Access Token may not have been granted (e.g. Tickets is a newer Intercom product area and may not be enabled on every workspace). Mitigation: a scope-missing response from Intercom (typically 403, mapped here to `unauthorized` since the vocabulary has no separate "forbidden" code) surfaces to the agent as a structured error rather than crashing; documented in the README as "some tools require the Tickets/Conversations product add-on to be enabled on the tenant's Intercom plan."
- Dependency: none on other tickets or repos — self-contained new connector.
- Dependency: connector wiki publish (`MSPbotsAI/mbagent-wiki`) happens in the review leg after INT publish succeeds, per `references/mcp-track.md` §4.5 — not a design-time dependency, noted so the review leg doesn't skip it.
